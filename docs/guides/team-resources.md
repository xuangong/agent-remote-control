# Transfer files between Team Hosts

Team resources transfer ordinary files through Relay storage without putting file bytes into the Team delivery queue. The sending and receiving Hosts can use different operating systems and working directories. A resource ID identifies bytes; a local path is meaningful only on the Host that returned it.

## Send and receive

1. On the sending member, call `upload_team_resource` with an absolute local `path` and an `operationId`. Uploads return `resourceId`, `name`, `mediaType`, `byteLength`, and `sha256` after the Relay verifies the complete file.
2. Call `send_team_message` with the usual recipient, operation identity, and text, plus `resources: [resourceId]`. Uploading alone does not send a message or grant another member access.
3. The receiving native session sees an attachment description such as `[resource #1]` with its stable ID. Call `download_team_resource` with that `resourceId`. Its result includes `localPath` and `verified: true` after checking file size and SHA256.
4. To return a report, upload the report on the receiving Host and send its resource ID back to the Leader. A member may forward a resource it received, subject to the same Leader/member communication rules.

The receiver can also read incoming messages through `read_team` while working. This tool returns complete incoming bodies in bounded pages (at most eight messages, with a 48,000-byte page target; a single message is never truncated). After reading a page, call `acknowledge_team_messages` with the IDs of the messages fully read before acting on them. Acknowledgement confirms receipt, not completion of their tasks. Follow `hasMore` and pass `nextAfterMessageId` as `afterMessageId` to read further pages. Sending status and recent settlement receipts are compact; the upload inventory is not repeated in tool results.

Explicit acknowledgement and automatic delivery compete for the same queue entry. An acknowledgement that wins removes the body and prevents later native injection. If native delivery has already claimed a message, acknowledgement refuses to clear it: inspect the delivery receipt instead. A successful acknowledgement can be retried with the same IDs while its settlement receipt is retained. Downloads do not acknowledge messages, and reading a message does not automatically consume it.

Files supplied through the Chatbox can be forwarded by uploading the verified local path made available to the agent. Do not send another Host's local path and assume it exists on the receiving machine. Downloading does not execute a file; any execution remains a separate native operation.

By default downloads go under the Controller's Team state directory in `downloads/<identity-hash>/`. `outputDirectory` selects an absolute directory on the receiving Host. Output names are generated from the resource identity and a sanitized display name. A matching existing file is verified and reused; a different existing file is never overwritten. Failed or corrupted downloads do not publish a completed local file.

## Limits and retention

Each file may contain up to 50 MiB, including a zero-byte file. Each message may attach up to eight unique resources totaling at most 100 MiB. Relay resource storage reserves at most 1 GiB by default. Upload and download chunks contain at most 32 KiB of file data.

Unreferenced uploads, including completed uploads that have not been sent, expire after 24 hours of inactivity. Upload admission performs storage cleanup; subsequent uploads also reclaim expired, unreferenced Team metadata. A Team retains at most 1,024 resource registrations. Sending validates and pins resources before durably accepting the message. Sent resources are retained for history and forwarding; archiving does not delete them. A storage failure after pinning and before message persistence can leave retained bytes without an accepted message. Quota exhaustion is explicit; the Relay never deletes referenced history to make room.

The 200-message and 128 KiB limits apply to the unresolved Team delivery queue, not lifetime traffic. The byte budget counts the stable enqueued identity, sender, receiver, text and creation time. It does not reserve hypothetical recipient space per message or count later delivery evidence; claims and settlement must remain possible when the queue is near capacity. Confirmed acceptance (except native queued input), explicit inbox acknowledgement, rejection and cancellation remove the message body and release capacity in the settlement commit. Dispatching, unknown and native queued input remain until settled; acceptance is not task completion. Existing settled inline history is compacted when Relay state is restored or next changed. Resource bytes travel in separate requests and are excluded from the queue budget. Resource metadata and delivery evidence remain bounded by their schemas and the shared 2 MiB Team state limit. Recipient grants survive dequeue independently of message bodies, so downloads and forwarding continue to work.

Controllers deliver as soon as the public session capabilities and current operation availability permit: idle sessions receive ordinary input; active sessions with steer support receive immediate input; otherwise active sessions with queue support receive next-turn input. An active turn waiting for a question or approval can still receive input if its adapter supports it; message delivery never answers the question or grants approval. Pending interactions without an active turn, reconnecting sessions and sessions without an available input capability wait. The adapter supplies native acceptance evidence. For Codex steer, a matching turn receipt confirms queue admission; a matching native user-message event confirms consumption. Task completion, idle state and elapsed time are not receipt evidence. No native Codex modification is required.

## Retry, authorization, and compatibility

Reuse the upload operation ID for the same file to query the accepted offset and continue interrupted uploads. Changing the declared name, size, media type, or digest under that identity is rejected. Reuse the message operation ID for the same message and resource list. Pending identities stay with the queue; settled identities retain only a fingerprint and outcome in Relay state. These receipts survive restart but expire after 24 hours, or earlier when the most recent 200 receipts / 32 KiB budget is exceeded, or when the shared Team state budget needs space. This is a bounded retry window, not lifetime deduplication. Within that window retries return the settled outcome without dispatching another native input; changed input conflicts. Outside it, inspect the receiving session before deciding to submit new work. The `read_team` tool exposes recent outcomes in `receipts`; ordinary Team catalogs and Host polls contain only unresolved messages. Receipt eviction never removes unresolved messages or resource grants. Message acceptance does not mean that a recipient downloaded, executed, or verified the file.

Resource calls authenticate the exact registered Host, Team, and member. Only the uploader and members explicitly addressed by a message containing the resource may read its bytes. Knowing an ID, seeing another member's metadata in a Team snapshot, or belonging to another Team is insufficient. Ownership and addressed-message grants survive a Relay restart with durable Team state and resource storage.

Resource support is negotiated separately from ordinary Team support. An updated Controller connected to an older Relay can still exchange text. Resource calls fail locally with an explicit unsupported message until the Relay supports and configures resource storage. No Borgee account or service is required.

Inbox acknowledgement is negotiated with `teamInbox=1` and the `teamInbox: 1` registration acknowledgement, in addition to exact-recipient support. An older Relay produces an explicit upgrade error before this new call is sent. Deploy the updated Relay and update participating Controllers to enable both inbox acknowledgement and timely busy-session delivery. Existing unresolved messages are retained; upgrading does not guess which old messages were read or replay uncertain native effects. Reopened native sessions receive the updated tools through the existing session extension mechanism.
