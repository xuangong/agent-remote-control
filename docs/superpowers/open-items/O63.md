# O63: Two Workbench tests still fail about once in 30 runs under heavy load

- Found in: the load runs that proved O60 and O61, 2026-11-22 (module split items 4 and 5)
- Owner step: owner
- Status: closed

## Item

The runs that proved O60 and O61 ran the Workbench suite four times in turn while five test files looped beside it (load average about 30 on 10 cores). Two other tests failed there:
- `App.succession.ask-and-reconnect.test.tsx` > "fences shared prompt editing from 'B' after awaiting 'native preparation' over HTTP and WebSocket": 2 of 60 file runs. The page showed "Handoff is not yet confirmed" with the fixture's "Fixture service unavailable." instead of the refusal ("no longer ready"): a status check reached the fixture, which does not serve `/succession/status`, and replaced the refusal before the test read it. Giving the dialog's timed status checks a 60 s first delay did not stop it, so the check is probably the immediate one a dialog makes when it mounts again with the stored operation (`recoverImmediately`); not confirmed.
- `components/SessionPromptEdit.test.tsx` > "returns the quotes an edited prompt carried to a view that receives quotes (true), and otherwise keeps them in its text": 1 of 4 suite runs, `receiveQuotes` not called. Possibly O62 (a discovery during the restoration); not confirmed.

Neither failed in the earlier runs at the base of this branch, which did not loop five files beside the suite.

## Cause

Both are tests that assert a state without waiting for the thing that produces it.

- `App.succession.ask-and-reconnect.test.tsx`: the refusal ("no longer ready") is an error of an uncertain handoff. The dialog checks such a handoff again 1 s after an error (`statusDelays[0]` in `SessionSuccessionDialog`), and every run, automatic ones included, clears the error before it asks. The test then clicks Details and waits for the text, which under load can take more than the real 1 s; the check reaches the fixture, which serves no `/succession/status` and answers 404 "Fixture service unavailable." The suspicion about `recoverImmediately` was wrong (it is only set when the dialog resumes a stored operation, which this test does not). Forced: with that delay remapped to 20 ms both the 'A' and the 'B' native-preparation cases fail every run with exactly the page text of the record. Fix: the test holds the 1 s check back for the length of the test (the delay remapped to 600 s, cleared when the page unmounts); the check is not what the test is about, and the product behaviour (a new check replaces an old error) is intended.
- `SessionPromptEdit.test.tsx` "returns the quotes ...": `usePromptEditOperation` hands the quotes back (`receiveQuotes`) after `composer.restore` has saved the prompt, which is later than the prompt showing in the editor, the state the test waited for before it expected one call. It is not O62. Forced: delaying the hand-back by 150 ms in the product fails the test with "expected vi.fn() to be called 1 times, but got 0 times", the record's symptom. Fix: the test waits for the call. With the delay in place the fixed test passes; the product is unchanged.

## Status

closed (2026-11-22). Both files pass (26 and 55 tests); no product change.
