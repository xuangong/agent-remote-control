# O65: Three WebKit component tests time out in the full component tier and pass alone

- Found in: the 0.3.4 release gate (3 WebKit timeouts, recorded in the release record) and the module split's two end gates, 2026-11-22
- Owner step: owner
- Status: open (not reproducible in a clean worktree; investigation recorded)

## Item

In two full `pnpm test:components` runs on one worker at the end of the module split (`52dfa735`, then `e70497d8`), the same three WebKit tests timed out at 30 s:
- `[webkit-ask-desktop] tpm-dock.spec.ts` > "TPM groups remain usable while multiple workspaces are open";
- `[orchard-phone-webkit] assistant-inventory.spec.ts` > "every element of the conversation is reachable" > "H1: Timeline header: REMOTE SESSION, agent id, status, epoch · seq → Replica Inspector (L3)";
- `[orchard-phone-webkit] phone-layout.spec.ts` > "at 390px the session stays fixed sideways while its conversation scrolls up and down".

Each passed 3 of 3 runs alone. The run is sequential and the machine was otherwise idle, so the cause is probably what the earlier specs leave in the WebKit process or the dev server, not load; not investigated

## Status

open (not reproducible in a clean worktree; investigation recorded, 2026-11-22, I5b). All three failures, in all three runs (`/tmp/rel034/components.log`, `/tmp/arc-split/gate-components.log` and `g2-components.log`), are the same: `page.goto` reached neither commit nor `load` in 30 s. The spec did nothing before the call. Each failure came at the 64th, 64th and 71st test of one WebKit browser: tpm-dock in `webkit-ask-desktop`, then H1, and phone-layout at 390 px after the worker restarted in `orchard-phone-webkit`. The same fixture pages had loaded in the tests just before.

What was checked in `.worktrees/i5-im` at `9c605844`:
- Two full `pnpm test:components` runs passed 1228 of 1228 (239 skipped, 17.4 min each), one with the gate's exact command (port 6175, outputs in the package) and one with port 6371 and outputs in `/tmp`.
- `webkit-ask-desktop` alone passed 63 of 63, also under `ulimit -n 256`.
- Sampled every 2 s for a whole project, WebKit's network process held 34 to 41 descriptors and at most 7 TCP connections, all direct to the dev server, not through the system proxy at 127.0.0.1:1082. At most 2 WebContent processes ran.
- The dev server logged only the proxy errors of the fixtures' `/v1` requests, about as many as in the failing runs. Vite ignores `test-results`.

So the cause is not a real wait or a fixture: the same pages load at the same place here. It is in what that worktree's run environment added to one WebKit browser instance by its 64th context. The code was the same; only docs and compatibility metadata changed between `e70497d8` and `9c605844`. The next full gate on another worktree closes this item if it passes, or records the browser's processes, descriptors and proxy route at the hang with the sampling above.
