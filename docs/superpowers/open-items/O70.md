# O70: Assistants are a directory over the Window groups, not their own record

- Found in: M3 of the [assistant tasks plan](../plans/2026-11-23-assistant-tasks-plan.md) (2026-11-23)
- Owner step: T1 of the [assistant tasks design](../specs/2026-11-23-assistant-coordinator-and-tasks-design.md)
- Status: open

## Item

`list_assistants` and `message_assistant` read the account's assistants from its Window groups (`accountDirectory` in
`agent-relay-core/src/assistants.ts`): an assistant's id is its group and view (`viewAssistantKey`), its name follows the account's
naming rule, and its main session is the session its view shows, which handoffs rebind. Design 5.2 asks for more:

- **The record.** No assistant record holds `name`, `picture`, `label`, `mode`, `coordinatorAccess`, `peers` or `limits`; names stay
  in `WindowBotDetails`. Moving a bot to another group gives it a new id, so a link and its reply chain start again.
- **Peers.** Every assistant of the account may message every other; nothing restricts it.
- **Coordinator and plain mode.** `mode` is stored in `WindowBotDetails` (absent is plain) until the record exists. The page offers
  the switch for every bot and starts every new bot as a coordinator, because it does not know whether the bot's Host runs tasks or its
  provider takes tools; a coordinator on OpenCode or DSH gets no tools, yet other coordinators can still message it. The Relay should
  learn which providers take tools from the Controller (as `readOnlyProvider` today) and the page should read it.
- **`coordinatorAccess`** (Q1, read-only main session) is not built.
- **Links whose session changed outside a handoff.** A link keeps the sessions it bound. When the person points a bot at another
  session, messages still reach the earlier one. A link member whose Host was offline is bound again only when the next message is
  sent.
- **Per-turn limits** (8.3): only the hop limit along a reply chain applies.

Fix: build the assistant record of T1 and let links and the directory read it.
