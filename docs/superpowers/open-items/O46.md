# O46: A terminal `codex exec resume` fails with "thread … already has an active writer" while a page shows the session

- Found in: M6
- Owner step: owner
- Status: closed as expected behaviour

## Item

A terminal `codex exec resume` fails with "thread … already has an active writer" while a page shows the session, and for minutes after it closes (the known issue M6 was asked to meet)

## Status

closed as expected behaviour (2026-11-21, owner's boundary in 5.7): a separate Codex process may not write a thread that the shared daemon has loaded; that is Codex's single-writer rule (`~/.codex/thread-writer-locks`), not ours, and we add no lock, release policy or handover for it. Measured with codex 0.171: a separate process is refused until Codex unloads the thread 60 to 70 s after its last client leaves (refused at +58 s and +60 s, accepted at +70 s and +75 s after `session release`). The terminal path that shares the session is the shared daemon (`agent-remote-controller codex exec resume <id>`, and for the instance `agent-remote-controller-dev codex exec resume|resume <id>`, which the development command now runs): both sides send, Codex orders the turns (a second turn while one runs is refused with "remote thread already has an active turn", and a page message during a terminal turn steers into it), and the page shows the terminal's turn from the daemon's own events in under a second (M6). How long our side holds the thread is O47
