# O40: The E3 flow 'the reader keeps their line when a Controller restart replaces the journal...' fails intermittently

- Found in: final end gate
- Owner step: owner, before deployment
- Status: closed

## Item

The E3 flow 'the reader keeps their line when a Controller restart replaces the journal...' fails intermittently: after the restart and a send, the reader's row moves 6,119 px

## Status

closed (78ad67b4): a product defect, not flow timing, and not a regression (item-key negotiation predates the baseline tag; no product source changed since a09d8fff, where the flow passed by the race). The page's trace on a failing run showed the first page served by the Controller (row keys without item keys, `codex:28:rewritten:r28`) and, after the restart, by the journal (`rewritten:r28`): every row key changed at once, `useTimelineScroll` found no row with the saved key and sent the reader to the first row (Row 30 from 476 px to 6,595 px). Which path served the first page was a race in loaded full runs (2 of 4 failed; 0 of 10 runs of the file alone); turning smart reading on for a session read from the Controller does the same every time (6,228 px, 2 of 2). O24's fix took the epoch out of the fallback key, but the fallback key and the item key still differ. The hook now keeps the anchored row element; when its key is gone, the one row with the same text is the same row (none when the text repeats, which keeps the old fallback). Pinned by 3 `useTimelineScroll` unit tests (2 of 2 mutations caught) and the E3 O24 flow, which now also turns smart reading on and restarts the Controller (fails on the old hook with 6,228 px). `test:e2e:flows` after the fix: 20 of 20 consecutive full runs passed (620 flows); on the instance with journals, turning smart reading on for a Claude session read from the Controller and restarting the instance changed every row key (`claude:1:...` to `user:...`) and the reader's row stayed at -2,584 px
